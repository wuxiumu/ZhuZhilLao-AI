# B站演示口播稿 v4（录制优化版）

> 主题：用“竹知了 AI 版”演示 FDE 工程师如何把一个想法做成可体验、可传播、可迭代的产品。
> 建议时长：6-8 分钟。
> 录制方式：屏幕录制为主，代码片段少量穿插。先展示结果，再解释设计。

---

## 0. 录制前准备

- 打开页面：`https://cgos.cc/zhuzhiliao-ai/`，本地录制可用 `http://127.0.0.1:8080/zhuzhiliao-ai/`
- 预先选好几个主题：OpenAI、Apple、NVIDIA、Bitcoin
- 浏览器放大到适合录屏的比例，避免 UI 太小
- 录制时先让声音正常播放，再开始正式口播
- 如果需要展示代码，优先展示：
  - `zhuzhiliao-ai/configs/openai.json`
  - `zhuzhiliao-ai/js/app.js`
  - `zhuzhiliao-ai/css/style.css`

---

## 1. 开场：先给结果（约 35 秒）

【画面】打开竹知了 AI 版页面，先选 OpenAI 主题，按住甩起来，让声音出现 2 秒。

【口播】

大家好，今天给大家看一个我最近做的小项目：竹知了 AI 版。

它的玩法很简单：打开网页，按住，画圈，甩起来。

【操作】手动甩一下，或者点“自动甩”。

你会看到这个 AI 公司 Logo 像小时候的竹知了一样转起来，背景里还会出现这个主题对应的企业语录。转动起来之后，背景语录会自动切换。

这个项目表面上是一个小游戏，但我更想用它讲一个工程师视角：一个 FDE，也就是偏全栈、偏交付的工程师，怎么从一个小想法出发，把它做成一个真的能玩、能分享、能迭代的产品。

今天不讲玄学，不讲大词，就看三个点：需求怎么收敛，功能怎么落地，反馈怎么继续驱动迭代。

---

## 2. 第一段：先做 MVP，不一上来堆技术（约 70 秒）

【画面】切到竹知了默认主题，手动甩起来。

【口播】

最开始这个项目的核心问题其实只有一个：能不能在网页里复刻“甩竹知了”的感觉？

如果从技术出发，很容易一上来就想做复杂：

- 要不要用 Three.js？
- 要不要上物理引擎？
- 要不要做成 React 项目？
- 要不要做 3D 模型？

但 MVP 阶段我没有这么做。因为第一个版本要验证的不是技术栈，而是体验本身。

用户真正关心的是三件事：

第一，手指甩动时，东西真的会跟着转。

第二，转起来以后，声音能出来，而且有速度变化。

第三，手机打开就能玩，不需要登录，不需要安装，也不需要等很久。

所以第一版的技术选择非常克制：原生 HTML、CSS、JavaScript，Canvas 负责画面，Web Audio 负责声音，自己写一个够用的绳系质点物理。

【画面】短暂切代码，展示 `app.js` 里的 `update` / `draw` / `ensureAudio` 附近即可，不要停太久。

【口播】

这里的重点不是“我不用框架所以更高级”，不是这个意思。

重点是：MVP 阶段要把技术复杂度压到最低，让项目尽快进入“可体验”的状态。

因为只有用户真的玩到了，你才知道这个方向有没有价值。

---

## 3. 第二段：把体验从“能玩”变成“愿意多玩一会儿”（约 80 秒）

【画面】快速切换几个主题：OpenAI、Anthropic、Apple、NVIDIA。

【口播】

第一版跑通以后，问题就变了。

能玩，不代表愿意一直玩。

一个声音、一个样式，用户试一下就结束了。所以第二步不是继续堆物理细节，而是增加可玩性和传播点。

于是我做了主题系统。

现在页面里有 15 个主题，分成三类：AI 公司、科技公司、加密货币。

【操作】切 OpenAI。

比如 OpenAI 是绿色主题。

【操作】切 Apple。

Apple 是银灰色。

【操作】切 Bitcoin。

Bitcoin 是橙色。

每个主题都有自己的 Logo、配色、背景语录和页面状态。

【画面】切到 `configs/openai.json`。

【口播】

实现方式也很直接：主题用 JSON 配置驱动。

也就是说，新增一个主题不需要改一堆业务代码，只需要加一个配置文件，再放一个 SVG Logo。

这就是我比较看重的工程取舍：不是为了架构而架构，而是让下一次迭代更便宜。

如果今天要加一个新公司，或者加一个新梗，它不应该变成一个重构任务。它应该只是一次配置更新。

---

## 4. 第三段：让“梗”和分享机制自然长出来（约 75 秒）

【画面】选择 NVIDIA 或 Bitcoin，展示背景语录；开始自动甩，等待语录切换。

【口播】

第三步是传播。

这个项目如果只是“竹知了在线版”，它是一个怀旧玩具。

但加上 AI 公司、科技公司、加密货币之后，它就变成了一个带梗的玩具。

比如 OpenAI、Anthropic、Apple、NVIDIA，每个主题都有自己的企业文化语录。

【操作】点自动甩，让背景语录变化。

而且我做了一个小细节：转动起来之后，背景里的语录会每 5 秒自动换一条。

这个设计的目的不是炫技，而是为了录屏和分享时画面不会太死。

你录一段 10 秒的视频，背景信息会有变化；你发给别人，别人也能看到这个主题的梗。

【画面】展示地址栏 hash。

还有一个小细节是 URL 记忆。

比如我现在选的是 OpenAI，链接里会带 `#openai`。如果我把这个链接发给朋友，他打开以后直接就是 OpenAI 主题。

这就是很小但很有用的增长设计：降低分享成本。

很多产品的传播不是靠一个巨大功能，而是靠这些细节叠加出来的。

---

## 5. 第四段：技术细节只讲跟体验相关的（约 90 秒）

【画面】展示页面，然后少量切代码。

【口播】

接下来讲几个技术点，但我只讲它们为什么服务体验。

第一个是物理。

这里不是严格的科学仿真，而是一个“体感正确”的模拟：手指是杆梢，Logo 圆盘是被绳子拉着的质点，中间有重力、阻尼、绳长约束。

用户不会问公式对不对，但他会感觉：这个东西是不是甩得起来，是不是有重量，是不是像小时候那个玩具。

第二个是声音。

声音不是按钮点击一下就播放，而是跟转速绑定。转得越快，声音越明显；停下来，声音就收掉。

这让操作和反馈之间有连接。

第三个是渲染。

背景、Logo、轨迹、UI 都在同一个页面里完成。为了保证手机上也流畅，静态背景会先画到离屏层，每一帧只绘制必要变化。

第四个是工程结构。

现在项目已经把 CSS 和 JS 独立出来：

- `css/style.css` 管视觉
- `js/app.js` 管交互、物理、音频、渲染
- `configs/*.json` 管主题数据
- `logos/*.svg` 管主题图标

这个结构的好处是后面继续加主题、改视觉、调交互，都不会挤在一个文件里。

所以技术细节不是为了显得复杂，而是为了让产品能继续演进。

---

## 6. 第五段：FDE 视角总结（约 70 秒）

【画面】回到页面，连续切换几个主题，最后停在 OpenAI 或 Apple。

【口播】

如果用 FDE 的视角回看这个项目，它其实不是“写了一个网页小游戏”这么简单。

它完整走了一遍从想法到产品的路径。

第一步，收敛需求。

不是一上来追求技术完整，而是先验证核心体验：能不能甩，能不能响，能不能马上玩。

第二步，快速交付。

用原生 Web 技术把它做成一个打开就能体验的页面，不让构建、部署、账号体系这些东西挡在用户前面。

第三步，根据反馈扩展。

当单一玩法容易腻，就做主题系统；当主题变多，就用 JSON 配置驱动；当希望更容易传播，就做 URL 记忆和分享。

第四步，持续优化体验。

比如刚才你看到的背景语录自动切换，就是为了让录屏和传播更自然。用户不会关心背后的实现，但会感受到页面更有生命力。

这也是我理解的 FDE：不是只写前端，也不是只写后端，而是能把需求、体验、工程和交付连起来。

【画面】停在一个效果最好的主题，点自动甩，让页面持续动起来。

【口播】

这个项目我已经放到线上，也会继续迭代。

如果你想体验，可以打开简介里的链接。你也可以试试不同主题，看哪个公司的语录被甩起来最有节目效果。

如果你对这种“小产品快速落地”的过程感兴趣，也欢迎在评论区交流。

后面我可能会继续拆这个项目，比如怎么做物理手感、怎么做 Web Audio、怎么把一个小玩具做成可传播的页面。

我们下期见。

## 9. 录制注意事项

- 开头 10 秒必须出现“甩起来”的画面和声音，不要先讲概念。
- 代码展示不要超过总时长的 20%，否则会变成代码讲解视频。
- “FDE”不要反复解释，观众记住“能从需求做到交付”就够了。
- 每讲一个技术点，都要补一句它服务的体验目标。
- 如果实际录制超过 8 分钟，优先删掉第 5 段里的部分技术细节，不要删开头演示和结尾总结。
